## 3. 分类算法与单位契约

### 3.1 最终规则树（已决，原顺序不可调整）

`ratio = PFR / VPIP`；由上而下，命中即停。以下 VPIP/PFR/WTSD 使用 **0–100 百分数**，AF 使用比率。CS 是输出 `'Calling Station'` 的缩写。

```text
if VPIP < 14:                          → Nit
elif VPIP >= 38 and AF > 3.5:          → Maniac
elif VPIP >= 38 and AF < 1.5:          → WTSD > 35 ? Calling Station : Fish
elif VPIP >= 28 and ratio > 0.7:       → AF >= 1.5 ? LAG : (WTSD > 35 ? CS : Fish)
elif 18 <= VPIP <= 28 and ratio > 0.7: → TAG
elif VPIP > 28 and ratio < 0.55:       → WTSD > 35 ? Calling Station : Fish
elif ratio < 0.55:                     → Fish
elif VPIP > 32:                        → AF >= 2.0 ? LAG : (WTSD > 35 ? CS : Fish)
else:                                  → TAG
```

样本 `<10` 返回 Unknown；`MIN_HANDS_FOR_CLASSIFICATION=10` 不变。新完整记录的分类sampleSize等于有效dealt player-hand；不完整历史记录则传**可同时可靠计算VPIP和PFR的有效核心样本数**，不能仅用dealt>=10掩盖有效样本不足。UI同时保留总handsDealt与核心覆盖数，样本不足占位判断也用分类核心样本数。该门槛是 UI 启用分类门槛，不代表十手足以统计验收。

### 3.2 单位边界（技术契约）

**不把仓库所有数据整体迁移成百分数。** `PlayerStats.vpip/pfr/gap`、`rangeEquity.safeVpip` 继续用 0–1；UI 仍乘100。新分类内核明确命名百分数入参，现有 `classifyPlayerType` 作为0–1兼容适配层，传入内核前转换一次；AF/WTSD extras 使用现有单位。直接内核测试传22/17，旧适配层测试传0.22/0.17，防重复或漏转换。

先检验有限数值与可行性 `0<=PFR<=VPIP<=100`；异常输入返回 Unknown 并保留诊断，不悄悄夹到有效范围伪造分类。VPIP=0 时先按 Nit 规则短路，避免计算0/0。比例边界测试用精确构造输入并锁定严格 `>` / `<`，不随意加 epsilon 改规则。

### 3.3 缺失 AF / WTSD

显式判空，不能让 JS 将 `null < 1.5` 当 true。AF缺失时规则2/3不命中，规则4/8的AF凶度判断为false；WTSD缺失不判CS。**不能称全树“AF缺失不判凶”**，规则5和TAG兜底不依赖AF。

AF零分母不能继续把“0进攻/0跟注”和“有进攻/0跟注”混成同一种 null。前置修复必须区分；推荐保留原始计数及可序列化状态（第9节），不要把 Infinity 直接写 JSON（会变成 null）。来源并未规定 Infinity 表示法；本仓库取 A/C 原始计数 + `no-calls` 状态，比较视为高于任意有限阈值但**不持久化 Infinity**（决策 37，P0a 已实现 `computeAFDetailFromEvents`）。

## 4. 性格目标区间（保留目标，非分类硬边界）

所有条件必须**联合**满足，不能分别挑选区间极值后形成不可行组合。保持 `PFR<=VPIP`，并满足目标ratio；例如TAG25/16虽然两个百分数各自落区间，但ratio=0.64不满足>=0.78，不能算目标通过。

| 类型     | VPIP%目标 | PFR%目标 | ratio目标 | AF目标  | WTSD%目标 | 校准说明                         |
| ------ | ------- | ------ | ------- | ----- | ------- | ---------------------------- |
| Nit    | 10–13   | 7–11   | —       | —     | —       | 首要是VPIP<14，PFR不超过VPIP        |
| TAG    | 20–25   | 16–20  | >=0.78  | —     | —       | 目标高ratio，不能靠TAG兜底掩盖行为不匹配     |
| LAG    | 28–36   | 24–30  | >=0.80  | >=2.0 | —       | 36不是分类硬上限；不等于超过38必Maniac     |
| Fish   | 38–45   | 12–17  | <=0.45  | <1.5  | <=30    | 高VPIP低PFR；不是所有被树判Fish都满足目标   |
| CS     | 38–45   | 12–17  | <=0.45  | <1.5  | >=36    | 必要宽度>=28；目标取38–45，36离阈值只有1pp |

### 7.3 范围与概率派生规则

**必要事实**：原F格是0概率，`0 × multiplier`仍为0；仅放大已有频率无法扩大入池范围。

推荐派生方案（技术细节仍待实施评审）：

1. 基表按原position/spot选择；169类组合用pair=6、suited=4、offsuit=12的组合权重计宽度，阻断牌/可用组合按当局另算。明确牌强排序/候选清单来源，不能把169格简单等权当组合数。
2. 为每个position/spot定义独立扩展候选及稳定强度序；扩大时从F转为C/R、收紧时从边缘C/R转F；面对3bet与RFI不能共用同一扩展列表。扩展次序、同强度tie-break须固定并有快照测试。
3. 原始动作权重`wR,wC,wF>=0`。先剔除当局非法动作，再应用频率变换并归一化：`p(a)=w(a)/sum(w)`；全零时返回合法确定性check/fold等fallback；所有概率在[0,1]且总和1。
4. threeBetFreq控制真实面对open时R与C/F的转移，不同时乘三者后任由总概率>1；callBias不能被“原分支无条件call”绕开。
5. 门槛示意：`valueThreshold'=clamp(base+valueShift,0,1)`；`callThreshold'=clamp(base+callShift(callBias),0,1)`。**callShift的映射函数尚需实施前固定**（推荐单调且基值1对应0），避免误用乘法让callBias更大反而更爱弃牌。
6. aggressionMult分别作用可选价值/诈唬权重，不把已被赔率/筹码/行动权限否决的动作重新启用。

不再承诺“控制流一行不动”；共享结构不等于可以不增加范围候选或策略权重层。所有无persona分支仍保持独立可回归性。

**实施决策（P6a 落地，2026-10-13）**：

- **恒等即原对象**：`preflopWidths(undefined)` 返回写死的 `{open:1, defend:1, threeBet:1}`（**不是** `PERSONALITY_PARAMS.TAG` —— TAG 初值恰好恒等只是巧合，会随 P9 校准漂移）。三档全 1 时 `derivePreflopRangeTable` / `rangeTablesForPersona` **直接返回基表对象本身**，连一次拷贝都没有；引擎侧所有概率表达式是 `× 1.0`（IEEE-754 下精确），所以无 persona 逐位不变、随机消费次数一个不增。
- **宽度按组合数**：`cellCombos` = 对子 6 / 同花 4 / 非同花 12，与 §7.3 第 1 条一致；强度序复用 `cellStrengthKey`（`getPreflopTier × 100 − Chen`，升序），`Array.prototype.sort` 在 ES2019 起稳定 → 同键保持 `(i,j)` 遍历序，扩展/收紧结果完全可复现并有快照测试钉住。
- **收紧复用一份实现**：`factor < 1` 时直接调用既有的锦标赛 `tightenCells`（保留最强部分、其余转 `donateTo`），不新写第二套收紧逻辑。
- **`facing` 两动作分开、顺序固定为先 C 后 R**：`C` 按 `defend` 缩放（放宽吃 `F`、收紧退 `F`），`R` 按 `threeBet` 缩放（放宽**先吃 `C` 再吃 `F`**、收紧退 `C`）。于是 `threeBetFreq` 是 **R 与 C/F 之间的转移**，`R ∪ C` 组合数守恒（实测：UTG 开池 → BB 防守，`threeBetFreq 1.6` 使 `R` 42→70、`C` 212→184，加进 `R` 的恰是从 `C` 拿走的 `AJs/AQs/JJ/KJs/KQs/TT`）。
- **赛制与性格的叠加顺序只有一处**：`rangeTablesForPersona(scenario, persona)` 先选赛制基表（锦标赛表本身就是从现金表派生的），再在其上派生性格；结果按 `赛制|三档倍率` 做**纯 memo**（`Map`），入参唯一决定结果、调用方一律只读 —— 这不是 `gtoConfig` 那种「可被外部改写的模块级 `let`」。
- **两个入口的赛制来源不同（既有契约，非本次引入）**：`decidePreflopGTO` 读全局 `getGtoConfig().scenario`；`getGtoPreflopRecommendation` 读 **query 里的 `gameScenario`**（渲染层 prop）。测试若只 `setGtoConfig({scenario:'tournament'})` 而 query 不传 `gameScenario`，走的仍是现金表 —— P6a 测试已按此修正。
- **`callShift` 映射推迟到 P6b，P6a 用乘性近似**：§7.3 第 5 条要求 `callThreshold' = clamp(base + callShift(callBias), 0, 1)`，并注明「映射函数尚需实施前固定（推荐单调、基值 1 对应 0）」。P6a 的启发式翻前只接了三档宽度，尚未接 `callBias`，因此这里落的是**乘性口径** `entryOdds(base) = min(base × callWidth, 1)`（`callWidth` = 开池场景 `openWiden`、面对加注场景 `defendVsOpen`），语义是「门槛随防守宽度等比放大、夹到 1」；`callBias` 在 P6a **完全未使用**。**推荐映射（P6b 固定并写测试）**：`callShift(b) = clamp(0.30 × ln(b), −0.30, +0.30)` —— 单调、`callShift(1) = 0` 精确、量级与现有门槛（0.08–0.48）同阶。P6b 落地时再决定它如何与宽度项组合（叠加还是相乘），并把该组合写进测试。**在 P6b 落地前，不得声称 `callBias` 已生效。** ⚠️ **此推荐式的符号在 P6b 落地时被纠正**：`0.30 × ln(b)` 对 `b` **递增**，会让 callBias 越大（越爱跟注）门槛反而越高 —— 正是 §7.3 第 5 条警告的「乘性用法让 callBias 更大反而更爱弃牌」的同型错误。实际实现用 `callShift(b) = clamp(0.30 × ln(1/b), ±0.30) = clamp(−0.30 × ln(b), ±0.30)`（**递减**：callBias 越大 ⇒ 门槛越低）。见下方「实施决策（P6b 落地）」第 1 条与 `449669e`。
- **启发式的真实杠杆已实测（重要，防止后续再踩）**：`decidePreflop` 里的 `isFacingRaise = ctx.toCall > 0` 语义是「我必须再掏筹码」，**非盲位恒为 true**（要补大盲注），而盲位没有任何位置标志 —— 于是 `ctx.isXxx && !isFacingRaise` 那棵开池树**对所有座位都不可达**（实测 BTN/CO/HJ/UTG 拿 A9o 时策略随机消费 **0** 次）。真正决定「要不要进池」的是**跟注价格门槛**（`entryOdds`）与**硬编码的反加概率字面量**（`raiseWidth`）。因此 P6a 用 `detectPreflopScenario(state, player) === 'rfi'` 选旋钮，而不是复用 `isFacingRaise`。`aceRaiseFactor` 的站点**全部**在 `!isFacingRaise` 块内（已逐站点核对），所以开池树的不可达不影响 `raiseWidth` 在可 reach 站点（tier 3/4/5 的盲位防守、tier 6）的正确性。

**实施决策（P6b 落地，2026-10-13）**：

- **`callShift` 映射已按推荐式固定（§7.3 第 5 条的待办项至此关闭）**：
  `callShift(b) = clamp(0.30 × ln(1/b), −0.30, +0.30)`，即 `CALL_SHIFT_SCALE = 0.30`。
  性质：`callShift(1) === 0` **精确**（`Object.is` 验为 `+0`）、对 `callBias` **单调递减**
  （越大越爱跟注 ⇒ 门槛越低，从根上避免「乘性用法让 callBias 更大反而更爱弃牌」）、
  关于 1 对称、有界 ±0.30（量级与现有门槛 0.08–0.48 同阶）、非法输入（`NaN`/负/0/`Infinity`）
  退回 0。六类实测：CS −0.1216、Fish −0.0787、Maniac +0.300（撞上界）、TAG 0、
  LAG +0.0316、Nit +0.0669。
- **P6a 的翻前乘性近似与 P6b 的加性门槛并存，不合并**：`decidePreflop` 仍用
  `entryOdds(base) = min(base × callWidth, 1)`（乘 `openWiden`/`defendVsOpen`），
  翻后各入口用 `shiftThreshold(base, callShift(callBias))`（加 `callShift`）。
  两者作用在**不同的旋钮与不同的街**上：翻前的 `callBias` 至今**仍未使用**，
  翻前跟注宽度由 `defendVsOpen` 表达；翻后的跟注门槛才由 `callBias` 表达。
  P9 校准时若要统一口径，必须重新评估翻前的 10 处 `entryOdds` 站点。
- **门槛平移一律用 `shiftThreshold(base, 0)` 原样返回 base（连 clamp 都不做）**：
  这是「无 persona 逐位不变」的实现保证之一。同理 `renormalizeAggression(w, p, 1)`
  逐位等于 `w`（因 `w + p === 1`），且已穷举验证本仓所有可达权重都满足
  `w + (1 − w) === 1`（42 个权重，0 例外）。
- **`aggressionMult` 的两种落法，按「有没有竞争权重」区分**：
  ① 有竞争的（中等牌价值下注 vs 过牌/跟注、边缘牌诈唬 vs 过牌/跟注、GTO 各档
  `catFreq`）走 `renormalizeAggression(w, 1−w, g)` 归一化，保守侧相对比例不变；
  ② 孤立的（`botAI.decidePostflop` 末尾那条「对手画像诈唬加注」）直接乘 `g` 并夹到 1；
  ③ **单位权重的无条件分支不乘**（GTO 无下注的 strong 分支权重恒 1）——
  `1·g/(0+1·g) === 1` 对任意 `g>0` 成立，乘上去只会引入 `g = 0` 的除零退化。
- **`renormalizeAggression` 的全零/`NaN` 必须收敛到 0 而不是 `NaN`**：
  `random() < NaN` 恒假会**静默禁用**动作，比返回 0 更难查（表现为「某类性格突然
  完全不下注」而没有任何报错）。
- **`valueShift` 在「门槛写在分档器内部」的引擎里，实现为权益下移**：
  `classifyPostflopHand(equity − valueShift, …)`。GTO 翻后与深筹码都用这个手法
  （深筹码新增 `config.classifyEquity` 字段）。**门槛判据仍必须用原始 `equity`** ——
  否则同一偏移会被算两次。对手画像的门（`equity < 0.5` / `< 0.4`）也用原始值：
  那是对手的门、不是价值门槛，§7.2 第 4 行要求 persona「保留对手调整」。
- **短筹码只能用范围当杠杆（实测）**：两个随机槽都已饱和
  （`random() < (1.0 + stealBoost)` 恒真、`random() >= defendTighten` 无画像时恒真），
  频率乘数是空转；深筹码引擎**零处 `random()`**，`aggressionMult` 无作用点。
  所以短筹码接 `openWiden`/`defendVsOpen`（**翻前**旋钮），深筹码只接门槛。
  §7.2 第 7 行「不以普通翻后参数假装已经覆盖」由此得到实测支撑。
- **短筹码范围派生复用 P6a 的实现，不写第二套**：把范围字符串摊成 13×13 表后交给
  `derivePreflopRangeTable`（组合权重、强度序、收紧/放宽算法与快照测试全部共用）。
  建表时**直接调用既有 `handMatchesRange`**，成员判定按构造一致、无漂移；
  `factor === 1` 时直接走原函数（不建表、不派生、零开销）。派生表按
  `字母|倍率|范围字符串` 做纯 memo。
- **`sizingMult` 全部推迟到 P6c**：§7.2 第 10 行要求「先变换下注或加注增量，再最终
  合法化；不能对已合法 amount 末尾裸乘」。翻后各引擎目前都是
  `Math.floor(totalPot × sizing)` 后直接交给 `calculateRaiseAmount` 夹到筹码上限，
  没有一个统一的「合法化层」可挂 —— 硬乘会重犯 §7.4 已复现的两个反例
  （加注增量不足最小全额加注 / 超筹码）。因此 P6b 三个提交都**没有**碰尺寸，
  `postflopParams().sizing` 已解析但尚未被任何引擎消费。（**已于 P6c-3 落地**，见下方
  「实施决策（P6c 落地）」。）

**实施决策（P6c 落地，2026-10-14）**：

- **顺序掷骰的条件概率分母只能是「保守权重内部的比例」**（P6b-2 的真实缺陷，`210180d` 修）：
  三动作分支（bet/check/call 顺序掷骰）要复现边际分布 `P(a) = w(a)·g^进取 / T`，
  第二掷必须是 `w_check/(w_check + w_call)` —— 一个**与 `aggressionMult` 无关的常数**。
  误写成 `w_check/(1 − p_bet)` 会让分母随 persona 变小、条件概率 **> 1**
  （`g = 2.5` 时 flop 中等牌算出 1.425，过牌分支恒触发）。现已落成三个命名常量
  （`MEDIUM_CHECK_GIVEN_NO_BET = 0.30/0.40`、`MARGINAL_CHECK_GIVEN_NO_BLUFF = 0.50/0.70`、
  `RIVER_MEDIUM_CHECK_GIVEN_NO_BET = 0.35/0.50`）并把推导写进注释。
  **P1 golden 抓不到这个缺陷**：它的翻后 case 都走「面对下注 + 强牌/大额加注」分支，
  没有一条落在「无下注 + 中等牌 + 掷两次骰子」的路径上 —— 是覆盖面问题，不是 golden 失效。
  ⚠️ 附带纠正两条一度写错的推理（都留档在源码注释里）：① 该缺陷在「commit 档 + 无人下注」
  下**观察不到**（`callThreshold` 归零 ⇒ 边缘分支直接 call，掷骰子前就被门槛截住）；
  ② 想「二分找 check→call 边界」在 NOBET 局面**测不出来**（`canCall` 要求 `toCall > 0`，
  动作恒为 check），改用**随机消费次数**当判据（1 次 raise / 2 次中等牌过牌 / 4 次落到边缘分支）。
- **河牌的阶梯与 flop 不同，不能照搬断言**：启发式河牌是强 0.70 / 中 0.50 / 边缘 0.30
  （比 flop 的 0.75/0.55/0.35 整体低一档，因为摊牌已无后续街），GTO 河牌是
  NUTS 0.85 / STRONG 0.75 / MEDIUM 0.50 / WEAK 0.30 **五档** + 「两对及以上抬地板到 STRONG」。
  河牌本来就没有听牌分支，所以 §7.2 第 5 行「不能生搬 flop 诈唬/跟注公式」在实现上
  表现为：只接**既有**门槛与频率，不移植任何听牌逻辑。
- **GTO 河牌三个入口共用 `getRiverStrategy`**，所以 persona 只在那**一个**纯函数里接线，
  机器人（`decideRiverGTO`）与面板（`getGtoRiverRecommendation`）一起生效、不会漂移。
  该函数把 `equity` 当**输入**，所以门槛/分档/频率的用例无需 mock 权益，完全确定性。
  §7.2 第 6 行「HU exact 权益分支保留」：persona **不碰**权益估计（一律来自
  `calculateRangeAwareEquity`），也不改迭代次数 ⇒ exact 分支逐位保留
  （golden 的 `river-gto-hu-exact` 钉住）。
- **`valueShift` 与门槛判据必须分开用两个权益值**（P6b-4 起的一致口径，河牌同样遵守）：
  分档用 `equity − valueShift`，**价格比较用原始 `equity`**。若两侧都扣，同一偏移被算两遍。
  对手画像门（深筹码的 `equity < 0.5` / `< 0.4`）也用原始值 —— §7.2 第 4 行要求
  「保留对手调整」，不能让 valueShift 把两个语义不同的判据耦合到同一旋钮。
- **`sizingMult` 的落点：一处纯函数 + 一处唯一汇流点**（P6c-3）。
  `scaleBetAmount(amount, toCall, minRaiseIncrement, maxAmount, sizing)` 只缩放**加注增量**，
  夹在 `[minRaiseIncrement, maxAmount]`；`sizing === 1` 时**原样返回**（逐位恒等）；
  已是全下 / 增量 ≤ 0（纯跟注）⇒ 不动；**只给「原本就是全额加注」的候选兜下限**
  （短全下型不兜 —— 否则缩放会把一个本来会被 reject 的金额洗成合法全额加注）。
  接线点是 `getBotAction` 末尾（六个入口的 `raise` 金额都从这里返回），
  而不是六个引擎各自的 `calculateRaiseAmount` / `createBetAction` —— 那样会散落六份实现、必然漂移。
  两层分工：`scaleBetAmount` 保证「缩放不主动造出非法金额」，reducer 侧 `legalizeRaise`
  保证「任何非法金额都进不了状态」。
- **尺寸的安全性是穷举证明的，不是抽查**：对**真实** `legalizeRaise` 穷举所有
  「变换前合法」的候选金额 × 六类 sizing，变换后仍合法、零违例。这条断言的意义在于
  reducer 拒绝 raise 时是 `return state` —— 动作被**静默丢弃**（不记统计、不换动作），
  所以「缩放不会让机器人空过一手」必须可证明，不能靠抽样。
- **面板一律不传 persona（P8b 才传）**：`getGtoPostflopRecommendation` /
  `getGtoRiverRecommendation` 都加了可选 `persona` 字段，但渲染层
  （`HandAnalysis`）**不传** —— 面板只服务真人，给的是「真人基础建议」，
  这正是 §7.2 第 8 行「不改变真人基础建议接口语义」的落地方式。
  但**面板与机器人共用同一套派生量**，所以一旦 P8b 传入，展示的门槛/频率就自动与
  机器人掷骰子所依据的数一致（含听牌「need X%」文案与判据同源）。
- **展示频率的取整口径逐站点核对过**：面板无下注的 strong 站点历史上是
  `round(f×100)` 与 `round((1−f)×100)` **各自独立取整**（和可为 101），
  与其余站点的「三数和恒 100」不同。穷举验证后确认该怪值在 strong 站点**实际不可达**
  （strong 档乘数恒 1.0 ⇒ `f` 只能是原始 CBET 值），但仍保留其独立取整写法，
  其余五站点才用 `mixFreq`。教训：归一化展示频率时不能一刀切，必须逐站点核对旧值可达性。

### 7.4 amount与合法动作契约

reducer的amount是**本次追加筹码**，不是raise-to。设`toCall=max(0,lastBet-player.bet)`：

- 无需跟注时：缩放bet的下注部分。
- 加注时：推荐只缩放`raiseIncrement=amount-toCall`，再形成`candidate=toCall+scaledIncrement`，不能把必须支付的toCall一起缩小。
- 在最终合法化层取整数筹码单位，校验finite、非负、筹码上限、最小全额加注、raiseRightsOpened和玩家自己的重开权限；不足全额加注但合法短all-in由规则单独处理。
- 超筹码候选按合法全下处理；权限不足时不得强行raise；候选退化为call/check/fold必须使用清晰的公共合法动作选择规则，并记录最终被接受动作。
- reducer拒绝动作时不能仍记一条统计事件；accepted action、记录amount与实际筹码差一致；每步和结算均检验守恒（允许显式买入/抽水项）。

已复现反例：bet20、lastBet100、toCall80、minRaise40、chips200，合法amount120直接×0.9变108，加注部分28不足40；amount180×1.6变288超筹码。现reducer防御不足，若复测证实则作为**独立合法性bugfix**，不是性格参数提交顺手修。

## 9. 聚合计数表与前置统计修复规格

### 9.1 聚合基础契约

基本单位是唯一`(containerHandId,playerId)` player-hand；新记录宜使用稳定全局手牌ID。每个成员必须在hand.players或可靠参与证据中；每项统计在目标玩家视图与**完整有序对手上下文**中计算原始计数，再按分配快照池化。

- 同手两个TAG是两份player-hand，合法分母+2；同一pair重复导入不能+2。
- 概率统计先加分子/机会分母再除：1/1与0/9合并=1/10=10%，不是均值50%。
- 不把一堆同类型事件拼成一个假玩家再调用按handId计数函数；这样会丢合法成员、串改事件归属。
- 各指标单独证据分母：缺失WTSD证据不能抹掉该手已知VPIP，也不能把未知摊牌结果记失败。
- 尽可能按整手重建历史计数；无法重建的指标提供覆盖数/缺失数，不能称100%专业正确。

### 9.3 AF零分母推荐表示

```text
A=0,C=0 -> state=no-actions, af=null
C>0     -> state=finite, af=A/C
A>0,C=0 -> state=no-calls, af=null，并保留aggressiveCount/callCount
```

推荐分类比较器读取计数状态：no-calls在数学比较中视为“高于任意有限AF阈值”，但**不持久化Infinity**；UI显示`∞（零跟注）`并附机会计数，样本量不足不冒称稳定Maniac。旧调用只提供af=null而无计数状态，则仍为缺失。**已决（决策 37），P0a 已实现 `computeAFDetailFromEvents`（A/C/unknownAllIns 计数 + 三态）**；其他平滑/封顶法须明确会改变边界，不静默实现。

共享计数内核让单座位与类型聚合一致；原`PlayerStats.af`可保持number|null，再增状态/计数字段，避免JSON丢信息与一次性改坏所有消费者。

### 9.4 前置修复范围与验收反例

用户已决“统计/场景先单独修”至少覆盖：整手VPIP/PFR、all-in进攻/跟注区分、AF零分母、WTSD全下runout、真实3Bet时序、CBet最后进攻者与机会、TurnCBet/FoldToCbet/CheckRaise上下文、WSD多人/边池可证实结果。缺证据要补生产或标未知，不能仅重命名统计函数。

每项各有聚焦测试：先call后raise、BB先check后raise、0金额动作、全下call与raise、无人跟注但多次进攻、无flop动作仍见flop、donk、多次翻前raise、check后面对CBet、两人同类型同手、同pid跨盘换类型、跨盘换真人/Bot、分母0、重复pair、多人平分与只赢边池。

这是行为修复：`rangeEquity`消费VPIP、会话画像消费计数，不能标成纯展示或零风险。

### 10.4 低迭代与真实迭代闭环

- 30–50仅为权益估计低迭代，**不是只打30–50手**。单局最坏二项近似标准误约7.1–9.1pp，不能据此验收绝对VPIP/WTSD。
- 生产迭代来源为equityIterations；纹理采样、短/深/GTO河牌等调用同时覆盖。`calculateEquity`第4参是iterations、第5参是options/range；不能以第3参numOpponents假装调用角色。
- HU河牌exact枚举不随MC iterations同比降耗，不能按迭代比例预测总耗时。
- 真实Player在headless模拟中需固定一种公开记录的代理策略；这是测试对手，不改变R1/B5的产品分配。对手政策、牌序、买入、每次seed和停止规则均记录，不能每次临时换策略比较数字。
- 建议预先固定至少5个独立seed、各类型覆盖全部位置；根据机会数而非仅总手数停止。示意资源下限：每类>=2000 player-hand、WTSD看flop>=400、AF跟注动作>=100，其他稀少机会>=100用于参考；**这些是初值（口径见决策43），不保证统计精度**。
- 比例报告95% Wilson区间、分seed/位置分布；ratio/AF按hand为cluster做bootstrap或报告原始A/C及跨seed稳定性；不能对相关动作当独立样本。CS最低目标36只有1pp分类余量，400flop通常远不足证明下界>35，需更多机会；通过口径见决策 43。
- 验收建议：联合目标区间 + 实测判回分配类型 + 多seed稳定性，样本未达精度为**不充分**而非通过；完整置信门槛见决策 43。不只凭全部样本池化后一个label盖过某seed严重漂移。
- 闭环runner走生产reducer/动作接受/计数逻辑，不手写第二套扑克引擎。普通jest自动收集`__tests__/**/*.test`；长闭环建议独立`scripts/`runner及显式校准命令，**不新增自动收集的30分钟calibration.test.ts**。
- 测试用独立干净存储，禁止清用户长期数据；按类型聚合本身会隔离旧Unknown，但空画像仍是实验控制条件。

## 11. 两行影子与座位标签显示契约

### 11.1 本手结束标签

使用共享settlement语义，当前`GameBoard.roundSettled = winner!==null || (phase==='showdown' && mainPot===0)`可作为核验起点；不能只看showdown/ended（全桌弃牌获胜仍可能保留preflop），也不能看revealed（管理员可提前亮牌）。

定义“有胜者”与“已分配完奖池”是否同一时点需在状态机上下文确认；展示应确保本手已无可行动作。下注阶段不出现性格文案；下一手清除settled后隐藏。关闭/未分配不虚构标签。

### 11.2 Bot Action固定两行

- 固定`Bot 紧凶Action`、`Bot 松凶Action`，对应当前Player假设由TAG/LAG决策；当盘没有这两类Bot、关闭性格也保留。
- 推荐无hero、缺完整手牌、已fold、all-in、筹码0、已结算/无行动权限时显示`— / 无可行动作`，不强算动作；两行不消失。是否非当前轮到hero也允许假设应保持既有面板语义并在测试注明。
- 策略seed/cache签名覆盖hero手牌、牌面、下注/权限、阶段、配置、persona、对手事件/画像版本。不同类型可用不同子流，但**不测试动作必须不同**。
- 两行共享一次相同权益/纹理/对手上下文；策略随机相互及真实Bot隔离。查询不得写统计事件或推进reducer。
- 全局setRandomSource临时切换仅适用于同步决策；如引入异步计算，应改为显式注入，防并发污染。性能验收记录实际MC调用次数与面板重复渲染开销，而非估算固定增加两倍。

### 12.2 前置翻前场景最小契约

场景不再从`lastBet>player.bet`或金额倍数猜测。只读**已被状态机接受**的翻前自愿加注链；强制SB/BB不是open，跟注式all-in不是raise。按顺序区分：

- **unopened**：尚无自愿投入/加注；非BB需要支付盲注仍然是未开池，不是facing-open。
- **limped pot**：已有自愿跟注但尚无open；BB可check，其他位置的隔离加注/跟注不能伪装标准无limper RFI。
- **facing open**：目标实际面对第一笔自愿加注；limp-raise也要按真实链确认，不能从“有toCall”推断。
- **facing 3bet**：目标已作open、后来收到首次再加注；原有自己的open事件不能丢。
- **cold 3bet机会**：目标此前未入池而面对open，拥有再加注权；与facing-open共享底层事实，只有策略选择层需要子类，不把尚未发生的动作记成已发生的3bet。
- **更高阶加注/短全下**：另保留raise序号和重开权限；金额不够全额加注不自动增加完整重开次数。目标作为第三方面对已发生的3bet应走冷防守/更高阶处理，不误落普通open范围。

当前`gtoPreflop.ts:974`的`isCold3bet`用`player.bet>0`判定“未入池”，并用其他玩家不同`bet`值个数>=2猜发生过二次加注——这仍是金额猜历史，不是读取真实已接受加注链。因此它不能当作P0d“真实场景”的可信实现，只是现状R分支的占位口径。枚举`cold_3bet`的实际使用语义必须先核对，再选择保留适配或明确拆名；不能仅把上面中文名替换字符串就改变其表查询含义。真实修复必须改为读取状态机已接受动作序列（或稳定携带的raise链），禁止沿用金额倍数推断。新spot识别与统计3Bet共享真实raise事实，但机会计数与策略选择是不同层。测试须包含多人先后行动、早已弃牌者、全下后无再行动者、同timestamp事件（用sequence或稳定数组顺序）。

### 16.2 P5 复核结论（一次被推翻的猜测，留档）

- P5 实施中怀疑「同盘内相邻两手也会撞旧手牌键」：旧键是
  `${handCounter}-${dealer}-${hero底牌点数}`，若同盘内两手 `dealer` 与 hero 底牌都相同，
  第二手会被当成同一手（漏建记录、动作并入上一手、结算覆盖长期库）。
- **实测推翻**：`handKeyRef` 只保存**上一手**的键，而 `RESET_ROUND` 每手把 dealer 轮转 1
  （`((dealer % N) + 1)`），所以 ≥2 人桌相邻两手的 dealer 必然不同（1 人桌不可开局，
  `MIN_TOTAL_PLAYERS = 2`）→ 同盘相邻手**不可能**撞键。
  （诊断方法：常数 `Math.random` 下打印每手的键，第 3 手与第 1 手键相同但 `prev` 是第 2 手的键。）
- 因此**没有**「同盘漏记一手」这个缺陷，不需要单独拆修；真正存在的既有 id 缺陷是
  **跨盘碰撞**（重挂载后计数归零），已由 P5 的 sessionId 修掉，并在 `f9389c0` 补了
  能守住它的回归用例（实测在等价旧公式下失败）。

### 16.3 P6a 复核结论（一个被实测推翻的实现假设，留档）

### 16.4 P6b 复核结论（四个被纠正的假设 + 一个测试技巧 + 一个测试坑，留档）

- **P6b-1 §7.3 的 `callShift` 推荐式符号是错的（方案勘误，非实现漂移）**：
  第 5 条写「推荐 `callShift(b) = clamp(0.30 × ln(b), ±0.30)`」。该式对 `b` **递增**，
  于是 callBias 越大（越爱跟注）门槛越高 ⇒ **越爱弃牌** —— 正是第 5 条自己警告的
  「避免误用乘法让 callBias 更大反而更爱弃牌」的同型错误，只是换成了对数形式。
  第 5 条的硬约束是「单调且基值 1 对应 0」，**没有指定方向**，所以实现必须自己定方向：
  采用 `callShift(b) = clamp(0.30 × ln(1/b), ±0.30)`（**递减**），并有测试钉住
  「对 callBias 单调递减」+「CS/Fish 为负、Nit/Maniac 为正」+「关于 1 对称有界」。
  原文已就地标注纠正，不改写历史措辞。
- **P6b-3 面板 `mixFreq` 差点引入显示回归（自查发现，未提交前修掉）**：
  最初把面板**所有** `freq` 站点都改成 `mixFreq(w, ratio)`（`bet/check/fold` 三数和恒 100）。
  但无下注的 strong 站点历史上是 `round(f×100)` 与 `round((1−f)×100)` **各自独立取整**，
  `f = 0.275` 时给出 `28/73/0`（和为 101）。**实测穷举后发现**：该站点可达的 `f` 只有
  `CBET × 1.0`（strong 档乘数恒 1.0），对全部 11 个可达 `f` 值两种口径**逐位一致**，
  所以 `28/73` 这个和为 101 的怪值在 strong 站点**实际不可达**。结论：strong 站点保留
  独立取整写法（并加注释说明为何不用 `mixFreq`），其余五个站点（facing strong/draw、
  无下注 draw/medium/weak/air）用 `mixFreq` 且已穷举验证与旧字面量逐位相同。
  **教训**：把展示频率归一化时，「和恒为 100」听起来更对，但会改变既有取整口径 ——
  必须逐站点核对旧值可达性，不能一刀切。
- **P6b-3 `valueShift` 的实现方向（推导纠正）**：§7.3 第 5 条写的是「门槛 `+valueShift`」，
  但 GTO 翻后的价值门槛全长在 `classifyPostflopHand` **内部**（strong 0.70 / medium 0.50 /
  weak 0.35 + 成牌下限），无法从外部「给门槛加一个数」。等价写法是**把权益下移** `valueShift`
  再分档：`equity ≥ floor + s ⟺ equity − s ≥ floor`。分档线因此在 `0.70 + valueShift` 处翻转
  （Nit `+0.05` ⇒ 0.75，CS `−0.12` ⇒ 0.58），测试用 ±0.01 探测翻转点逐类钉死。
  **同一手法也用于 P6b-4 的深筹码**（新增 `config.classifyEquity = equity − valueShift`）。
- **P6b-4 短筹码「频率是空转」（实测推翻直觉）**：短筹码的两个随机槽
  `random() < (1.0 + stealBoost)` 与 `random() >= defendTighten` 在无对手画像时**都已饱和**
  （恒真），给频率乘 `aggressionMult` 完全无效。真正决定进池的是**范围成员判定**，
  所以 persona 必须落在 push/defend 范围上（用翻前的 `openWiden`/`defendVsOpen`，
  **不是**翻后参数）—— 这正是 §7.2 第 7 行「不以普通翻后参数假装已经覆盖」的实测依据。
  同理深筹码引擎**零处 `random()`**，`aggressionMult` 在那里也没有作用点，只有门槛可改。
- **测试技巧：常数随机源二分精确测混合概率（P6b-3 起用）**：要断言 `random() < p` 的 `p`，
  大样本计数有二项波动、种子选不好会偶发红。改用「把策略随机源设成**常数** `v`，
  在 `v ∈ [0,1]` 上二分」—— 因为 `probe(v)` 对 `v` 单调（`v < p` ⇒ 进取），二分能把 `p`
  定到 1e-9、零波动。前提是该分支只掷**一次**骰子（air/medium/draw 分支都满足）。
  这条比「数 200 个种子里有多少 raise」稳得多，P6c 河牌的混合频率也应沿用。
- **测试坑（已修）**：`sixMaxPlayers` 早期把 hero 第二张底牌的花色写死成 `♥`，
  于是听牌用例的 A♠4♠ 悄悄变成 A♠4♥ —— 牌面只有 3 张黑桃，`detectDraws` 给不出同花听牌，
  `'draw'` 分支整条测不到（引擎侧听牌是从**真实底牌**重检测的，不像面板可直接传 `draws`）。
  修法：`SpotOpts.handSuits` 显式传 `['♠','♠']`。**教训**：构造听牌局面时必须显式控制
  两张底牌的花色，不能依赖辅助函数的默认值。

### 16.5 P6c 复核结论（一个自查出的真实缺陷 + 三条被推翻的推理 + 一个证明方法，留档）

- **P6c-fix：P6b-2 自己引入了一个真实缺陷（自查发现，独立 commit 修正）**
  这是本轮最值得留档的一条，因为它是**已提交代码**里的错，不是设计阶段的口误。
  P6b-2 把 `decidePostflop` 两处顺序掷骰的第二掷分母从常量改成了 `1 − p_进取`，
  看起来「更一致」，实际是错的：三动作分支（bet/check/call 顺序掷骰）要复现边际分布
  `P(a) = w(a)·g^进取 / T`，第二掷必须是 `w_check/(w_check + w_call)`，一个**与
  `aggressionMult` 无关的常数**。错写在 `g = 2.5` 时算出 **1.425 > 1**
  （过牌分支恒触发），`P(check)` 从正确的 0.158 变成 0.21。
  - **为什么当时没被抓到**：`botAI.personaPostflop` 的用例只比较了「无 persona vs TAG」
    和「加注率高低」，两者都对；P1 golden 的翻后 case 全部走「面对下注 + 强牌/大额加注」
    分支，**没有一条**落在「无下注 + 中等牌 + 掷两次骰子」的路径上。
    是覆盖面缺口，不是断言写错。
  - **怎么发现的**：写 P6c-1 河牌时，因为河牌有同构的 `0.35/(1−0.50)` 写法，
    我回头去核对 flop 侧的推导，才发现两者都被我改坏了（河牌侧尚未提交，
    flop 侧已提交）。
  - **教训（已写进源码注释，防止再犯）**：顺序掷骰的条件概率分母**只能**来自
    「保守权重内部的比例」，任何让它随 persona 变化的写法都要怀疑。
    三个常量（`MEDIUM_CHECK_GIVEN_NO_BET`、`MARGINAL_CHECK_GIVEN_NO_BLUFF`、
    `RIVER_MEDIUM_CHECK_GIVEN_NO_BET`）都带完整推导注释。
- **被推翻的推理 ①：「这个缺陷在 commit 档下无 persona 也生效」**
  我一度认为边缘牌分支的错写在 commit 档（`bluffMultiplier` 归零）会改变无 persona 行为
  ⇒ 是个更严重的回归。**实测推翻**：commit 档把 `callMargin` 归零 ⇒ `callThreshold` 变 0 ⇒
  边缘分支最后的 `equity >= callThreshold` 恒真、直接返回 `call`，掷 check 骰子之前就被
  门槛截住了。所以那个组合下**观察不到**差异。已把这条写进源码注释，避免后人按错误推理改代码。
- **被推翻的推理 ②：「二分找 check→call 边界就能钉住常量」**
  最初用「找 check 变 call 的临界 `v`」写测试，实测返回 1（测不出来）。
  原因：NOBET 局面下 `canCall` 为假（`canCall` 要求 `toCall > 0`），中等牌过牌失败后
  落到边缘分支、最终**也是过牌** —— 动作恒为 check，区分不出 `v` 在边界的哪一侧。
  改用**随机消费次数**当判据：`v < p_bet` ⇒ 1 次、`p_bet ≤ v < X` ⇒ 2 次、
  `v ≥ X` ⇒ 落到边缘分支再掷两次 = 4 次；谓词 `randomCalls ≤ 2` 对 `v` 单调，
  翻转点恰是 `X`，完全确定性。
- **被推翻的推理 ③：「河牌的 `sizingMult` 可以先裸乘，反正有 `legalizeRaise` 兜底」**
  §7.4 反例 1 说明这不成立：裸乘 `120 × 0.9 = 108` 会得到「增量 28 < 最小全额加注 40」，
  `legalizeRaise` 返回 `reject`，而 reducer 拿到 `reject` 后是 **`return state`** ——
  机器人的动作被**静默丢弃**（不记统计事件、不换动作），表现为「轮到它却什么都没发生」。
  兜底在这里不是「降级成合法动作」，而是「动作消失」。所以缩放必须在合法化**之前**
  保住全额加注下限，这正是 `scaleBetAmount` 存在的理由。
- **证明方法：安全性用穷举而不是抽查**
  `botAI.personaSizing.test.ts` 对**真实** `legalizeRaise` 穷举所有「变换前合法」的
  候选金额 × 六类 sizing，断言变换后仍合法、零违例（数千组合，并带
  `expect(tested).toBeGreaterThan(5000)` 防空断言）。
  理由同上：后果是「机器人静默空过一手」，这种缺陷靠抽样测不出来、靠 review 也容易漏，
  必须可证明。同类手法还有短筹码的「放宽 ⇒ `base ⊆ derived` / 收紧 ⇒ `derived ⊆ base`」
  集合包含断言（不依赖具体范围表内容，169 格逐格比对）。

### 16.8 P8b 复核结论（一处机制选择 + 两处口径 + 两个坑，留档）

- **「两行共享一次权益」的机制选择（先调研后定，三种机制里选一种）**
  §11.2 要求两行共享一次相同权益。调研结论：**纹理已共享**（`boardTexture.analyzeBoardWithEquity`
  按牌面 memo）、**对手上下文**由 `(player, state)` 确定性推出（无随机）⇒ 两行天然相同；
  **只有权益未共享** —— `calculateRangeAwareEquity` 是蒙特卡洛（`Math.random()`），
  在 `getBotAction` 可达路径上有 **6 个调用点**（`botAI:960/1170`、`gtoPostflop:152`、
  `gtoRiver:627`、`gtoShortStack:465`、`gtoDeepStack:603`）。
  三种机制：① 显式参数注入要改五个模块签名（触碰 P1 golden 风险最大）；② 不共享不满足契约；
  ③ **作用域缓存**（最终采用）只改 `rangeEquity` 一处 + `getShadowBotActions`，
  与既有 `setRandomSource`、`boardTexture` 牌面 memo **同型**，**零引擎签名变更 ⇒ P1 golden 风险为零**。
  ⚠️ 它的前提是**同步调用链**（面板在渲染期同步跑两行）—— 若将来引入异步计算，
  必须改成显式注入，否则并发的两个作用域会互相污染（`rangeEquity` 注释已写明这一条）。
- **`shadowSeed` 的 persona 只能「条件追加」，不能无条件追加**
  第一版无条件把常量 `'auto'` 追加进签名，把**默认路径**的种子也改了 —— 症状是
  `botAI.test.ts` 的「局面变化会换抽样」用例翻红（`Expected: > 1, Received: 1`），
  而**不是**报「随机被污染」。改成 `...(assumedType === undefined ? [] : [assumedType])`
  后默认路径逐字不变。**教训**：任何「给既有签名加一维」的改动，都要先确认
  **不传该维时**签名与改动前逐字相同 —— 与 P5 的 `beginSession` 不消耗随机源是同一类坑。
- **两行**不**测试「动作必须不同」（§11.2 明示）**
  混合频率下两行本来就允许给出同一个动作，所以断言只能落在「都是合法动作词」。
  这条同时意味着：**两行的差异不能当作 persona 生效的证据** —— 证据要落在数据层
  （`botAI.shadowRows` 的**共享权益次数**、独立子流），而不是渲染层的动作对比。
- **`handAnalysis.botAction` 是死键，本步删掉**
  单行改两行后 `botAction: 'Bot Action'` 全仓无引用（已 grep 确认），连同其注释一起删除，
  避免留下「看起来还在用」的旧文案。新增三键：`botActionTAG` / `botActionLAG` /
  `botActionUnavailable`。
- **测试坑：面板在摊牌时**整体**不渲染**
  `PlayerArea` 的门控是 `canShowHand && player.isRealPlayer && !isShowdown && phase` ——
  即**整块面板**在摊牌时消失，所以「已结算 ⇒ 两行显示占位符」这条**只能在直接渲染
  `HandAnalysis` 的组件测试里覆盖**（真实 UI 走不到）。这是既有面板语义，不在本步改动范围
  （§11.2 末句要求「保持既有面板语义」）。
- **面板在渲染期调决策引擎的既有约束（本步未变，但值得记一笔）**
  `getShadowBotActions` 走的是与真机器人**完全同一条**决策路径，只在随机源上做了隔离；
  两行还共享一次权益 ⇒ 面板每换一次局面只多付**一次** MC（不是两次）。
  §11.2 末句要求「记录**实际 MC 调用次数**与面板重复渲染开销，而非估算固定增加两倍」，
  两条证据都已实测：
  - **MC 调用次数**（`botAI.shadowRows.test.ts`，spy 计数）：
    `separate === shared × 2` 且 `shared > 0`；不可行动局面为 **0 次**。
  - **重复渲染开销**（esbuild 打包 cjs + `node`，翻牌局面、取 40 次最小值）：
    单行 `getShadowBotAction(TAG)` **65.0ms**（1 次 MC）／
    两行 `getShadowBotActions` **65.1ms**（共享后仍 1 次 MC）／
    两次独立 `getShadowBotAction` **128.7ms**（2 次 MC）。
    ⇒ 两行 / 单行 = **1.00 倍**（第二次决策的纯逻辑相对 MC 可忽略），
    独立两次 / 单行 = **1.98 倍**；**共享相对不共享省 49.5%**。
    即「面板从单行改两行」**没有**增加可观测的渲染成本 —— 这个量级由 MC 主导。

### 17.1 P9-4 参数校准结论：最佳可达 + 结构性缺口（2026-10-15）

P9-4 用 P9-3b 的闭环 runner 在**生产迭代**下实测（5 seed × 600 手 = 3000 手；每类
≥2000 player-hand、看翻牌 ≥400、AF 跟注 ≥100，机会数**全部达标**），得到一张
「最佳可达」参数表（`src/utils/botPersonality.ts` 的 `PERSONALITY_PARAMS`，逐值断言见
`botPersonality.test.ts`）。**§4 的目标区间是工作目标**，本轮实测确认其中若干维度在
当前引擎下**参数不可达** —— 按决策「最佳可达 + 记录缺口」处理：**不改分类树、不改
§4、不改引擎**。

**实测（`scripts/reports/p9-4-final.md`；3000 手 / 33321 次决策 / 生产迭代 / 被拒 0）**：

⚠️ **低迭代初筛不可用于验收（本轮再次验证 §10.4）**：同一张参数表在 40 次迭代 /
1000 手下的 AF 与生产迭代差很多（Fish AF 低迭代 3.35 → 生产 1.98），所以低迭代只用于
找方向，结论一律以生产迭代为准。

**三条结构性缺口（本轮确认，未修）**：

1. **ratio 维度整体高于引擎可达上限**。§4 要 TAG ≥0.78 / LAG ≥0.80，§3.1 分类器主规则
   也要 `ratio > 0.7`；但实测 ratio 上限约 **0.63–0.69**（Nit 0.693 / TAG 0.627），且与
   VPIP **负相关**（低迭代探针里 TAG VPIP 压到 18.9 时 ratio 才 0.640，代价是 VPIP 掉出
   区间）。根因是**翻前加注分支被 `!isFacingRaise` 门控**：`isFacingRaise = ctx.toCall > 0`
   对非盲位恒真（要补大盲注）⇒ RFI 的 `ctx.isXxx && !isFacingRaise` 开池树**对所有座位
   不可达**（§16.3 早已记录），入池几乎全走 `entryOdds` 跟注 ⇒ 「加注/跟注」比例由硬编码
   字面量（最大 `0.22 × raiseWidth`）锁死，参数改不动它。**推论**：TAG/LAG/Maniac 的 ratio
   目标、以及 LAG(24–30) / Maniac(32–45) 的 PFR 目标在当前引擎下**参数不可达**。另：
   `threeBetFreq` 确实是 PFR 杠杆（TAG 7.9 → 14.8），但它在 ~5 就饱和，且它把 `R` 从 `C`
   搬走、在抬 PFR 的同时压 ratio —— 两个目标共用同一旋钮且方向相反，无法同时满足。
2. **Fish 的 `WTSD ≤ 30` 与「松被动」语义相悖**。VPIP 38–45 的玩家看翻牌多、跟注多，
   WTSD 必然偏高（实测 50.2）；同一份 §4 给 CS 的目标却是 `WTSD ≥ 36`（高）。两条目标
   语义方向相反，Fish 的 ≤30 在「高 VPIP + 多跟注」下不可达 —— 这不是旋钮量程问题。
3. **Maniac 未被 runner 覆盖**。runner 的固定桌型（R1/B5，6 人）按 §5 的 A′ 配额只分到
   TAG/LAG/Fish/Nit/CS 五类，Maniac 未进入采样 ⇒ **无实测数据**，其参数保持 §7.1 初值
   （未校准）。同理 `sizingMult` 的量级也只经过间接验证（`botAI.personaSizing` 的穷举
   安全性测试，不是闭环实测）。

**P10 待办（要让上述目标可达，须先动引擎；本轮按「失败不得改分类树」未做）**：

- **翻前加注作用点（唯一能让 ratio/PFR 目标可达的修法）**：让非盲位在 RFI 能真正选到
  开池树（用 `detectPreflopScenario` 选树，而不是复用 `isFacingRaise`），使 `openWiden`
  能分别表达「加注宽度」与「跟注宽度」。这是**引擎行为变更**，须独立提交 + P1 golden
  复核 + 全量回归；影响面覆盖所有非盲位的翻前决策，风险最高。
- 若确认 ratio 维度不可修，则需重估 §4 的 ratio 目标**与** §3.1 的 `ratio > 0.7` 主规则
  阈值（二者同源）—— 属验收口径变更，须先拍板。
- **Maniac 采样**：把 runner 的桌型扩到能覆盖 Maniac（或单开 Maniac 专用跑法）后再校准。
- Fish 的 `WTSD ≤ 30`：若确认为语义错误，应改成与 CS 同向的高 WTSD 目标（口径变更）。
